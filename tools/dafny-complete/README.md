# dafny-complete

**Does your Dafny contract pin down a single result?**

Dafny proves that a method satisfies its `ensures` clauses. It does not tell you whether those
clauses say *enough*. A contract that only constrains the length of the output, or only says
"the result is a well-formed number", verifies just as green as a complete one, and the method
can still be wrong.

`dafny-complete` checks, for every method, that the postcondition admits **exactly one result**
for each valid input. When it does not, it shows you a **concrete witness**: an input and two
different results that both satisfy every `ensures` clause.

```
$ dafny-complete lru.dfy

  [UNDER] lru_cache  line 11    the contract accepts two different results
                      input  : capacity=1, ops=[(0, 0, 0), (0, 0, 1)]
                      out = [-1, -1]   (what the method returns)
                      out = [0, -1]    (also satisfies every ensures)
```

Here the only postcondition was `ensures |out| == CountGets(ops, |ops|)`: the method is fully
verified, yet nothing says *which* values a `get` returns. (It was, in fact, buggy.)

## Why this exists

We asked LLM agents to solve 8 algorithmic tasks in Dafny, with complete specifications required
([VerifBench](../../bench/)). Every solution verified. But for the smaller model, **5 of 8
contracts barely constrained the result**: an addition specified only as "the output is a
canonical decimal" (`"0" + "0"` may return `"1"`), a topological sort allowed to return `[]` for
an acyclic graph, a path normalizer allowed to return any non-empty string. Four of those methods
happened to be correct; one was not, and the proof did not notice.

When code is written by agents, a weak specification is worse than none: it produces **false
confidence**. `dafny-complete` makes that visible. The full story:
[Green proofs, empty promises](https://dev.to/malek_aitouaret_f026758c/green-proofs-empty-promises-when-ai-agents-write-their-own-specifications-59lf).

## Install

Requires Python 3.9+ and [Dafny 4.x](https://dafny.org) on your `PATH` (with Z3).

```bash
pipx install "git+https://github.com/quod-lang/quod#subdirectory=tools/dafny-complete"
```

## Usage

```bash
dafny-complete file.dfy                    # check every method
dafny-complete file.dfy --method Foo       # only Foo (repeatable)
dafny-complete file.dfy --json             # machine-readable, e.g. for an agent
dafny-complete file.dfy --no-witness       # uniqueness proof only (faster)
```

Exit code: `0` no underspecified method, `1` at least one underspecified (handy in CI), `2` tool error.

| Verdict | Meaning |
|---|---|
| `[OK]` determined | Dafny **proved** that the contract allows a single result. |
| `[UNDER]` underspecified | A witness was found: two different results, each **proved** to satisfy the contract. |
| `[?]` inconclusive | No uniqueness proof, no witness. The contract may be complete but need a lemma to show it. |
| `[skip]` | Not checked (no outputs, no `ensures`, instance method, heap access). |

Both `[OK]` and `[UNDER]` rest on Dafny proofs, never on testing. An `[UNDER]` verdict is never a
false alarm.

## How it works

For each method `M(x) returns (r)` with `requires R` and `ensures E`:

1. **Uniqueness.** It generates
   `lemma Uniq(x, a, b) requires R(x) && E(x, a) && E(x, b) ensures a == b {}`
   and asks Dafny to prove it, with no hints.
2. **Valid inputs.** If that fails, it generates small inputs from the parameter types and keeps
   those for which Dafny proves `R(x)`.
3. **Real answers.** It compiles and **runs `M` itself** on those inputs to get `a`.
4. **Witnesses.** It builds neighbours `b` of each answer (a changed digit, a dropped element,
   an emptied line...) and asks Dafny to prove `E(x, a)` and `E(x, b)`. Both proved and `a != b`:
   a certain witness.

The contract is copied verbatim into a generated predicate; your file is never modified (the
generated files sit next to it while the tool runs, then are deleted; `--keep` keeps them).

## Prior work

The idea of checking a Dafny specification by mutating outputs on concrete inputs and asking the
verifier comes from **Shuvendu Lahiri, [Evaluating LLM-driven User-Intent Formalization for
Verification-Aware Languages](https://arxiv.org/abs/2406.09757)** (FMCAD 2024), which scores
specification completeness against test cases. `dafny-complete` builds on the same idea and
differs in that it needs no tests (it runs the method itself), adds a universal uniqueness proof
over all inputs, and only reports a witness when Dafny *proves* that the contract accepts it.
More in [docs/related-work.md](../../docs/related-work.md).

## Limitations

- Witness search covers `int`, `nat`, `bool`, `char`, `string`, `seq<T>` and tuples. Other types
  still get the uniqueness proof.
- Instance methods and methods with `modifies` / `reads` / `old(...)` are skipped for now.
- Neighbours are generated by simple rules: a contract can be incomplete in a subtler way and
  come out "inconclusive". In our benchmark, the 6 truly underspecified methods all got a
  witness, and the 3 inconclusive ones were in fact complete (canonical forms whose uniqueness
  needs induction).
- "Determined" means *complete*, not *right*: a contract can pin down a single wrong result.

## Part of Quod

`dafny-complete` is the first building block of [**Quod**](../../), a programming language
designed to be written by AI agents and checked by machines, where this check is built into the
compiler (with an explicit `loose` clause for methods that legitimately allow several results).
