# Backend C# : note de conception

État : le générateur et ses tests sont faits ; l'intégration à .NET (paquet, MSBuild) reste à faire.

## But

`quod build fichier.quod --target csharp` génère un fichier `.cs` qui s'ajoute à un projet .NET
existant et s'appelle comme n'importe quelle bibliothèque C#. Le code doit garder les garanties
prouvées, rester lisible par un développeur C#, et ne dépendre que de la bibliothèque standard.

**Le cas d'usage visé** est du code métier : des règles pures écrites en Quod (par un agent, le plus
souvent), appelées depuis une application C# qui garde les entrées-sorties. Le backend de la 0.2 ne
suffit donc pas à lui seul : il faut aussi les types de la 0.3, et ce qui manque à la feuille de
route (voir [Au-delà de la 0.2](#au-delà-de-la-02)). Il doit être conçu pour les accueillir.

**Hors périmètre :** traduire du C# vers Quod, vérifier du C# existant, générer des projets entiers.

## Le problème principal : les appelants ne sont pas vérifiés

Entre fonctions Quod, chaque `requires` est prouvé à chaque appel. Un appelant C# ne prouve rien : il
peut passer une liste non triée à `binary_search`, et obtenir une réponse fausse sans aucune erreur.
Le backend Python a le même trou, mais on l'y remarque moins ; dans une application métier, c'est par
cette frontière que passera chaque appel.

Vérifier tous les `requires` à l'entrée ne convient pas non plus. Celui de `binary_search` ci-dessous
est un double `forall` : le vérifier à chaque appel coûterait O(n²) sur une fonction en O(log n).

**Décision :** une fonction publique vérifie par défaut les `requires` sans quantificateur, et
`null`, ce qui coûte peu. Les `requires` quantifiés sont vérifiés seulement avec une option
(`--check-requires all`), et le commentaire de la fonction dit clairement lesquels restent à la charge
de l'appelant. Les appels entre fonctions Quod ne vérifient rien. La violation lève une
`ArgumentException` qui cite la clause.

Les `ensures` restent sans code : ils sont prouvés pour toute entrée qui respecte les `requires`.

## Correspondance des types

| Quod | C# | Raison |
|---|---|---|
| `int`, `nat` | `System.Numerics.BigInteger` | Les preuves supposent des entiers non bornés (voir ci-dessous) |
| `bool` | `bool` | |
| `seq<T>` | `IReadOnlyList<T>` | Pas de copie à l'entrée, une `T[]` ou une `List<T>` s'y convertit sans effort |
| `(T1, T2)` | `(T1, T2)` (`ValueTuple`) | Idiomatique ; `t.0` devient `t.Item1` |

**`BigInteger` et non `long`.** Avec `long`, un dépassement pourrait contredire une preuve valide ; ce
serait un bug que le langage promet d'exclure. Le coût est mesuré : une boucle de somme sur 5 millions
d'éléments prend environ 107 ms contre 3 à 5 ms en `long` `checked`, soit un facteur 25 à 35 (une seule
machine, sous charge, à refaire proprement). C'est sans importance pour une règle métier, et gênant
pour une boucle de calcul intensif.

La sortie correcte à terme est dans le langage : des types `i32` et `i64` dont l'absence de dépassement
est une obligation de preuve. Une simple option `--int long` serait fausse, car elle changerait le sens
d'un programme déjà prouvé. Ces types serviraient aussi l'interopérabilité, car presque toute l'API
.NET parle `int`.

## Forme du code généré

Un fichier `Nom.g.cs` par fichier Quod. Une classe statique `Nom` dans un espace de noms (`--namespace`,
`Quod.Generated` par défaut). Chaque fonction donne une méthode publique en PascalCase, qui contrôle la
frontière, et une méthode privée `_quod_f_nom`, celle que le code Quod appelle, récursion comprise (un préfixe,
car C# refuse d'appeler une méthode qu'une variable locale du même nom cache) :
c'est la structure à deux étages du backend Python. Les lemmes ne sont pas générés.

Source ([bench/quod/binary_search](../../bench/quod/binary_search/solution.quod)), sans ses invariants :

```rust
fn binary_search(xs: seq<int>, target: int) -> int
  requires forall i in 0..len(xs): forall j in i..len(xs): xs[i] <= xs[j]   // sorted
  ensures -1 <= result < len(xs)
  ensures result >= 0 ==> xs[result] == target
  ensures result == -1 ==> forall i in 0..len(xs): xs[i] != target
  loose (r1, r2) => (r1 == -1) == (r2 == -1)
```

Sortie visée, écrite à la main. Ce fichier précis compile sans avertissement en `netstandard2.0` avec
C# 7.3, s'utilise depuis un projet `net10.0` en `Nullable` activé, et rend les bons résultats sur quelques
cas :

```csharp
// <auto-generated>Generated by quod from solution.quod. Do not edit.</auto-generated>
using System;
using System.Collections.Generic;
using System.Numerics;

namespace Quod.Generated
{
    public static class Solution
    {
        /// <summary>Proved by quod.</summary>
        /// <remarks>
        /// ensures -1 &lt;= result &lt; len(xs)
        /// ensures result &gt;= 0 ==&gt; xs[result] == target
        /// ensures result == -1 ==&gt; forall i in 0..len(xs): xs[i] != target
        /// loose (r1, r2) =&gt; (r1 == -1) == (r2 == -1)
        /// NOT CHECKED, the caller's duty: forall i in 0..len(xs): forall j in i..len(xs): xs[i] &lt;= xs[j]
        /// </remarks>
        public static BigInteger BinarySearch(IReadOnlyList<BigInteger> xs, BigInteger target)
        {
            if (xs == null) throw new ArgumentNullException(nameof(xs));
            return binary_search(xs, target);
        }

        private static BigInteger binary_search(IReadOnlyList<BigInteger> xs, BigInteger target)
        {
            BigInteger lo = new BigInteger(0);
            BigInteger hi = new BigInteger(xs.Count);
            while (lo < hi)
            {
                BigInteger mid = lo + Div(hi - lo, new BigInteger(2));
                if (xs[(int)mid] < target)
                {
                    lo = mid + new BigInteger(1);
                }
                else if (xs[(int)mid] > target)
                {
                    hi = mid;
                }
                else
                {
                    return mid;
                }
            }
            return new BigInteger(-1);
        }

        // Euclidean division, as in Quod and SMT-LIB: the remainder is always >= 0.
        private static BigInteger Mod(BigInteger a, BigInteger b)
        {
            BigInteger r = BigInteger.Remainder(a, b);
            return r.Sign < 0 ? r + BigInteger.Abs(b) : r;
        }

        private static BigInteger Div(BigInteger a, BigInteger b)
        {
            return BigInteger.Divide(a - Mod(a, b), b);
        }
    }
}
```

**Compatibilité : deux cibles réelles**, .NET Framework 4.7.2 (donc C# 7.3) et .NET Core ou .NET récent (C# 8
ou plus). Le code généré se limite donc à C# 7.3, sans API propre à une plateforme : pas de `record`, pas
d'expression `switch`, pas de type référence nullable, pas d'`UnreachableException`. L'en-tête
`<auto-generated>` met le fichier hors du contexte `Nullable` du projet. Le même exemple, avec un tuple et
`EnsureSufficientExecutionStack`, a été compilé et exécuté en visant `net472` (C# 7.3, sur le CLR 4.8 de la machine
de test) et `net8.0` (C# 8).

Sur .NET Framework, `BigInteger` exige une référence à `System.Numerics`, absente d'un ancien `.csproj` par
défaut : c'est au paquet `Quod.Build` de l'ajouter, sinon le fichier généré ne compile pas.

**Pas de bibliothèque d'exécution** : les fonctions d'aide sont privées et générées dans chaque fichier,
seulement si elles servent. Aucun paquet à déployer ni à maintenir en phase.

## Les pièges, là où C# diffère de Python

Le backend Python ne les rencontre pas ; chacun demande un test dédié.

| Piège | Conséquence | Réponse |
|---|---|---|
| `==` sur `IReadOnlyList` compare les références | Égalité de séquences fausse, sans erreur de compilation | `EEq` généré selon le type : une fonction d'aide structurelle, récursive pour les séquences et les tuples imbriqués. Vaut aussi pour `ValueTuple.Equals` |
| Division tronquée | `-7 / 2` vaut -3, et -4 en Quod | `Div` et `Mod` ci-dessus, vérifiés sur les quatre combinaisons de signes |
| Débordement de pile | **Tue le processus, sans exception possible**, là où Python lève `RecursionError` | `RuntimeHelpers.EnsureSufficientExecutionStack()` en tête des fonctions récursives : sur une récursion très profonde, l'exception `InsufficientExecutionStackException` a bien été rattrapée, sur les deux cibles. Sur un serveur web, un débordement tuerait tout le processus de l'application, d'où ce choix |
| Index `int` | L'API veut un `int`, Quod a un `BigInteger` | Conversion `(int)` : l'indice est prouvé dans les bornes, et une conversion impossible lève `OverflowException` |
| « Pas de retour sur tous les chemins » (CS0161) | Refus de compiler après un `while`, alors que c'est prouvé | `throw` final quand la dernière instruction n'est pas un `return` |
| Portée des blocs (CS0136) | `if c { let x = 1; } let x = 1;` est accepté par Quod (vérifié) et refusé par C# | Renommer les variables des blocs imbriqués à la génération |
| Mots réservés | `class`, `string`, `params`... | Préfixe `@`, prévu par C# pour cela |
| Noms publics | `foo_bar` et `FooBar` donnent la même méthode | Erreur à la génération, jamais de renommage silencieux |
| Liste vide `[]` | C# 7.3 n'infère pas son type | `new T[0]`, le type venant de `TExpr.Ty` |

**Construire une séquence dans une boucle.** `r = r + [x]` devient `r.Add(x)` sur une `List<T>` quand
aucune autre variable ne peut la voir, sinon ce serait quadratique. C'est l'analyse `appendable` du backend
Python : elle doit passer dans un module commun, pas être recopiée. La fonction peut renvoyer cette liste
telle quelle : un appelant pourrait la retransformer en `List<T>` et la modifier, mais elle n'appartient
alors plus qu'à lui.

**Quantificateurs dans le code exécuté.** Une fonction d'aide `All(lo, hi, i => ...)`, avec arrêt au premier
échec, comme le `all(...)` de Python.

**`--runtime-checks`.** Même sémantique qu'en Python : `requires`, `ensures`, invariants et `assert` non
prouvés deviennent des contrôles. Ils lèvent une exception dédiée, jamais `Debug.Assert`, retiré en Release,
pour la raison qui exclut `assert` en Python.

## Intégration à .NET

Par étapes, chacune utile seule :

1. **`quod build --target csharp`** et l'argument `target` de l'outil MCP `quod_build`. `Pipeline.generate`
   reçoit la cible au lieu d'appeler directement le générateur Python.
2. **Un paquet NuGet `Quod.Build`** avec une cible MSBuild : les `<QuodCompile Include="**/*.quod" />` sont
   vérifiés avant `CoreCompile`, et le `.g.cs` s'ajoute à la compilation, avec reconstruction incrémentale.
   Une preuve qui échoue fait échouer la compilation du projet. Il doit fonctionner dans les deux mondes : le
   MSBuild de Visual Studio et `dotnet build`, un projet SDK et un ancien `.csproj` avec `packages.config`. D'où
   un appel de `quod` comme exécutable (`Exec`) et non une tâche MSBuild chargée en mémoire, qui devrait exister
   pour les deux environnements d'exécution.
3. **Les diagnostics au format MSBuild** (`fichier(ligne,colonne): error QUOD0001: message`) : ils arrivent
   dans la liste d'erreurs de Visual Studio et dans les journaux de CI, sans autre travail.
4. **Des directives `#line`** vers le `.quod` : les piles d'appels et le débogueur montrent la source Quod.
5. **`dotnet tool`** pour l'installation. Le compilateur est publié en Native AOT avec z3 à côté ; à vérifier :
   la prise en charge des outils propres à une plateforme par le SDK .NET 10, et la façon d'y joindre z3.

**Temps de vérification.** Une preuve peut prendre des dizaines de secondes, ce qui n'est pas acceptable à
chaque compilation. La cible MSBuild ne doit donc revérifier que les fichiers changés. Un cache par contenu de
fichier et version du compilateur irait plus loin. Le budget par défaut reste à fixer selon l'usage.

## Validation

Le générateur ne fait pas partie de ce qui est prouvé : une erreur de traduction casserait la garantie sans
que rien ne le dise. Il lui faut donc plus de tests qu'à un autre composant.

- **Trois exécutions comparées.** Le compilateur a déjà un interpréteur (`Eval`) : sur chaque programme des
  exemples et du banc, avec des entrées tirées comme pour les contre-exemples, l'interpréteur, Python et C#
  doivent rendre le même résultat.
- **Les tests cachés de VerifBench** à travers C#, sur les six solutions de référence : le même score que
  Python est attendu. `hidden.py` charge un module Python ; il lui faut un petit exécutable qui lit les cas en
  JSON et rend les résultats.
- **Une compilation réelle en CI**, avec les avertissements traités comme des erreurs : `net472`/C# 7.3 (sur Windows,
  avec exécution des tests) et .NET récent. Un projet ancien format avec `packages.config` pour `Quod.Build`.
- **Un test par piège** du tableau ci-dessus.
- **Un bras `quod-csharp` du banc** n'a pas d'intérêt tant que l'agent écrit la même chose : l'agent écrit du Quod,
  la cible ne change rien pour lui. À ne pas mesurer avant que ça change.

## Au-delà de la 0.2

Le backend doit laisser la place à ces types. Les correspondances sont des intentions, à confirmer avec la conception
de chacun.

| Prévu | C# envisagé | À décider |
|---|---|---|
| chaînes (0.3) | `string` | **La sémantique :** UTF-16 de C#, points de code, ou octets UTF-8. `len(s)` et `s[i]` en dépendent, et chaque backend devra rendre la même réponse |
| types algébriques, `Option` (0.3) | classe abstraite et classes imbriquées scellées, avec égalité générée | Pas de `record` : C# 7.3 l'exclut. Les appels se font par `is` et `switch` à motifs de C# 7 |
| modules (0.3) | espaces de noms et classes statiques | Un `.cs` par module ou par programme |
| génériques (0.3) | génériques C# | L'égalité structurelle, à porter à travers `T` |
| cartes et ensembles (0.4) | `IReadOnlyDictionary<K, V>` en interface | Sans paquet : `System.Collections.Immutable` est absent de .NET Framework, et un paquet y ajoute des redirections de liaison |

**Ce que du code métier demandera et que la feuille de route ne prévoit pas encore :**

- **`decimal`** : tout montant. Sa théorie côté solveur n'est pas évidente, car il est borné et arrondit.
- **Dates et durées.**
- **Des enregistrements à champs nommés**, plus lisibles que les tuples ; les types algébriques peuvent les couvrir.
- **Des entiers bornés** (`i32`, `i64`), vus plus haut.
- **L'appel de code C# depuis Quod**, avec un contrat que le vérificateur croit sur parole : c'est une frontière de
  confiance à rendre visible dans le rapport, comme `loose`.

## Lots proposés

Les lots 1 à 5 sont faits : les six solutions de référence passent tous leurs tests cachés à travers C#
(`verifbench.hidden_csharp`), et les programmes du dépôt rendent les mêmes résultats que l'évaluateur, en .NET 10
comme en `net472` avec C# 7.3. Les noms privés de l'exemple ci-dessus sont devenus `_quod_f_nom`, `_quod_div` et
`_quod_mod`. L'argument `target` du MCP (dans le lot 6) est fait aussi.

1. Extraire ce qui est commun à Python (`appendable`, le filtrage des lemmes) ; aucun changement de comportement.
2. `CodegenCSharp.fs` et `--target csharp` : entiers, booléens, séquences, tuples, sans `--runtime-checks`.
3. Les trois exécutions comparées et la compilation en CI, avec un test par piège.
4. Le contrôle de la frontière et `--runtime-checks`.
5. Tests cachés de VerifBench à travers C#.
6. MCP, puis `Quod.Build` et les diagnostics MSBuild. La 0.2 sort ici.
7. `#line`, cache de vérification, `dotnet tool`.

## Décisions prises

1. **Contrôle de la frontière :** `null` et les `requires` sans quantificateur par défaut, le reste avec
   `--check-requires all`.
2. **`BigInteger`** seul en 0.2, les entiers bornés plus tard.
3. **Compatibilité** : C# 7.3, pour .NET Framework 4.7.2 et .NET Core ou récent.
4. **Noms publics** en PascalCase.
5. **Après la 0.2**, la 0.3 commence par la sémantique des chaînes, qui conditionne le reste.
